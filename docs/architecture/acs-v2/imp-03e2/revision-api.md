# Workforce revision API

## Endpoint

```text
POST /api/v1/workforces/:workforceId/revisions
```

The endpoint creates exactly one immutable successor revision. The request must identify the expected current revision and supply the complete successor composition.

## Request body

```json
{
  "expectedRevision": 2,
  "displayName": "Research Workforce",
  "purpose": "Coordinate research tasks",
  "members": [],
  "compositionConstraints": [],
  "authorityRefs": [],
  "membershipPolicyRef": {},
  "auditPolicyRef": {},
  "changeReason": "Update composition",
  "idempotencyKey": "workforce-revision-3",
  "requestedAt": 2000
}
```

`members` must be a non-empty array of canonical `WorkforceMemberV2` values. `compositionConstraints` and `authorityRefs` are arrays of canonical entity references. `membershipPolicyRef` and `auditPolicyRef` are canonical revision references. The route validates identifiers, references, timestamps, and member shapes before command construction.

## Semantics

- The new revision number is `expectedRevision + 1`.
- `supersedes_revision` is the expected revision.
- The successor preserves the Workforce identity and scope.
- Agent selectors and role references are carried as explicit revision references; current Agent heads are not substituted into historical records.
- The canonical fingerprint is generated by `createWorkforceRevisionV2`.
- The route emits `workforce.revision.created` through the Native Core command and returns the resulting current Workforce view.
- Retrying the same idempotency key and request hash returns the original result without appending another revision.
- A stale expected revision returns HTTP `409` with the existing `conflict` envelope and `reason: stale_revision`.

## Response

Successful creation returns HTTP `201` with the standard Product API envelope containing the updated identity, current revision, current composition, and revision commit metadata. The canonical revision remains addressable through the existing revisions read endpoint.
