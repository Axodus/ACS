**Status:** READY_TO_EXECUTE

## 1. Purpose

E16-M1-S00 is the mandatory pre-execution sprint for EPIC-16. It converts the approved normative package into an implementation-ready contract without changing production behavior.

The sprint must answer, with repository evidence, exactly what economic truth already exists, which authority owns it, how it reaches the Product API and Dashboard today, which fields/projections are missing, and what the smallest safe E16-M1 implementation slice is.

No feature implementation is authorized in S00.

## 2. Sprint outcome

At S00 closure, the coder must be able to begin E16-M1-S01 without rediscovering domain boundaries or making product decisions during implementation.

Required terminal result:

```text
E16-M1-S00: PASS
EPIC-16 EXECUTION READINESS: READY
AUTHORIZED NEXT SPRINT: E16-M1-S01 — Economic Read-Model Contract
```

If authoritative source ownership or a decision-gated financial boundary cannot be resolved, S00 must close as `BLOCKED` rather than inventing a contract.

## 3. Mandatory work packages

### S00-WP01 — Economic domain inventory

Inspect and record the concrete implementation locations for:

- `EconomicService` and economic operations;
- quote/pricing policy and quote identities;
- reservation state and release semantics;
- authorization hooks and applicable governance/limits;
- usage/metering records and run correlation;
- settlement provider, projections, receipts and idempotency;
- reconciliation implementation;
- economic repositories and PostgreSQL shared-state composition;
- audit/event correlation;
- Product API economic routes/contracts;
- Dashboard economics consumer contract at the current `dev` head.

Deliverable: a file-level authority map in `execution-readiness.md` using exact repository paths and symbols.

### S00-WP02 — Canonical terminology matrix

Freeze operator semantics for at least:

- quoted;
- estimated;
- authorized;
- reserved;
- metered/usage-recorded;
- settled;
- released;
- reconciled;
- exception/mismatch;
- unavailable;
- zero;
- not applicable.

For every term, identify the existing source object, whether the value is authoritative or derived, persistence expectations and permitted UI representation.

Do not normalize distinct domain concepts into one generic `cost` field.

### S00-WP03 — Source-of-truth and provenance map

For each planned E16-M1 output field, record:

1. source service/repository;
2. durable identity/provenance available today;
3. Tenant key;
4. execution/run correlation key;
5. timestamp/version source;
6. unit/currency-like unit semantics where applicable;
7. degraded/unavailable behavior;
8. whether historical reconstruction is possible without fabrication.

Any field without an authoritative source must be classified `UNAVAILABLE`, `DERIVATION_REQUIRED`, or `NOT_AUTHORIZED`.

### S00-WP04 — Product API surface inventory

Document current economic endpoints and identify the proposed M1 read-only boundary. The proposal must distinguish:

- summary projection;
- list/search projection if justified;
- detail projection if justified;
- provenance/evidence references;
- stable unavailable/empty/error semantics.

S00 may propose names and payload shapes but must not implement routes.

### S00-WP05 — Dashboard integration inventory

Inspect the financial regions introduced/preserved by baseline `9005e3a` and classify every displayed financial value as:

- authoritative live value;
- truthful zero;
- truthful unavailable/empty state;
- derived value with documented source;
- unsupported/fabricated — must not exist.

Produce the exact data-contract delta expected from M1. Do not redesign Dashboard hierarchy in S00.

### S00-WP06 — Acceptance and fixture strategy

Define the minimum deterministic test fixtures/scenarios for M1:

- Tenant with no economic activity;
- quoted/estimated-only execution;
- active reservation;
- usage without settlement where valid;
- successful settlement;
- released reservation;
- reconciliation mismatch where existing primitives allow it;
- dependency/provider unavailable state;
- cross-Tenant access rejection.

Each scenario must define expected Product API semantics and expected Dashboard/Control Plane representation without synthetic financial history.

### S00-WP07 — Open-decision disposition

Confirm the following remain outside M1 implementation unless a normative amendment exists:

- invoice generation/issuance;
- payment capture or money movement;
- tax computation;
- accounting journals;
- unrestricted manual financial adjustment;
- commercial provider expansion beyond the approved adapter boundary.

If current code already exposes adjacent behavior, document it as inherited evidence; do not broaden it.

### S00-WP08 — Execution decomposition freeze

Validate or amend the proposed M1 execution sequence:

1. `E16-M1-S01` — Economic Read-Model Contract;
2. `E16-M1-S02` — Pricing Provenance;
3. `E16-M1-S03` — Product API Exposure;
4. `E16-M1-S04` — Dashboard Integration;
5. `E16-M1-S05` — Acceptance and Milestone Closure.

For each sprint, specify exact implementation boundary, principal files/modules, tests, non-goals and commit boundary.
